# 管理员调整充值订单票种与税费

## 操作流程

在充值账单中选择一笔成功订单，点击票种编辑，选择普通发票、专用发票或不开票，点击“预览税费调整”。系统显示实付金额、调整前后开票费用、钱包增减、调整后余额和当前宽限额度。核对后保存。

增加税费会扣减钱包，减少税费会返还钱包，不会向支付账户付款。扣款后余额为负数时，管理员必须勾选负余额确认；欠额不得超过系统 `InvoiceTaxConfig.refund_overdraft_limit_cents`，单位为分，0 表示不允许新增负债，没有固定10元或20元上限。已经为负的账户继续扣款同样要求确认；返还余额不会因为原欠额超宽限而被拒绝。

只允许当前启用的管理员或 root 操作，财务、客服和普通用户不能修改。Default、Classic 行为一致。原来仅修改票种、不同步税费的写接口已被替换，旧客户端不能绕过预览直接保存。

## 计算口径

原支付金额保持不变，目标开票费用由当前生效政策计算。已生效的 gross_up 政策为普通发票6%、专用发票9%，不开票为0；历史免费普通发票按原截止时间规则保留。未启用固定政策时沿用配置的税费模式和税率。这里的开票费用与发票法定增值税率是不同概念。

- 目标净额 = 原支付金额 - 目标开票费用。
- 目标付费额度 = round(首次调整前的付费额度 × 目标净额 ÷ 首次调整前的净额)。金额用分，额度用整数 quota，四舍五入一次。
- 钱包增减 = 目标付费额度 - 当前订单付费额度。
- 调整后钱包 = 当前钱包 + 钱包增减。
- 显示余额 = quota ÷ 系统额度单位；不能把税费的人民币金额直接当作 quota，也不重新套用当前汇率、充值价格或折扣。

例如订单实付100元、原不开票，原净额100元、付费额度50000000，钱包1000000，额度单位500000：改为专票后费用9元、净额91元，目标付费额度45500000，扣4500000，显示余额2变为-7。宽限至少7元且管理员确认后可执行；改回不开票则返还4500000。往返始终引用首次基准，避免整数舍入反复累积收益。

订单实付金额、支付流水和赠送额度保持原值；有效净额、税费、付费入账额度及充值额度显示同步更新。后续开票按新税费快照处理，已预付部分不会再次收税。后续退款按调整后的付费额度计算，同时仍受原实付现金上限约束。

## 适用范围

需要可确认人民币的成功充值，并有完整、内部一致的 `CheckoutVersion=1` 支付、净额、税费和付费入账快照。赠金来源不可改为现金来源。缺少可信快照的历史订单拒绝直接调税，不自动估算其原税费或混合赠金。

存在待开具/已开具发票占用的订单不能修改。用户存在待处理或已完成退款时也拒绝本入口：修改任意旧付费来源的容量可能重排消费 FIFO，破坏已有退款凭据；不能仅检查本订单是否有正数退款分摊。此类历史账务需另行核对，不能用提高宽限绕过来源或占用检查。

## 事务、审计与部署

POST `/api/user/topup/invoice-type/preview` 只预览；PUT `/api/user/topup/invoice-type` 提交相同 `id`、`invoice_type`、`expected_invoice_type`，并携带预览 `revision` 和需要时的 `confirm_negative: true`。

两步均重新核验数据库角色，事务先锁用户，再锁管理员、订单与配置；MySQL 的一致性读取必须在用户锁之后。余额、票种、配置或前次调整发生变化会使旧预览失效。每次扣还、订单更新、凭据插入都在同一事务中，检查影响行数；任一步失败全部回滚。零差额不执行用户余额更新，避免 MySQL 未变化行数为0导致误判。

新增 `top_up_invoice_adjustments` 保存操作人、时间、首次换算基准、脱敏订单与余额前快照、结果。revision 唯一，重试返回原结果，不再扣还；旧凭据是历史记录，不代表当前余额。订单快照不包含支付网关密钥。提交后失效用户缓存并记录带金额的管理日志。

部署时需要后端迁移和双主题更新。本次仅提交源码，未部署或修改生产数据。历史三笔退款已经执行的优惠扣回不在本功能中重放。

验证覆盖 SQLite/MySQL/PostgreSQL 的扣还、幂等、并发申请互斥、过期预览、宽限及回滚；前端覆盖负余额确认、超宽限禁用、修改选择清空预览和桌面/手机布局。
